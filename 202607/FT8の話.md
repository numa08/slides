# 無線を知らない人に知ってもらいたい FT8 の話

裏テック無尽 2026/07/03 @numa08

## 無線？FT8？何の話をしようとしているの？
FT8とは
「微弱電波で遠く離れた無線機同士がデジタル信号でデータをやり取りするためのオープンなプロトコル
数ワットで射出された電波が空気中を伝って地球の裏側とか宇宙に到達したときに、他の電波のノイズや電波自身の減衰でデータが欠損しても
77bitという限られたデータで `どうにか交信を成立させてやろう` という執念の仕様」

個人的な感想
今回資料を作るにあたり改めてFT8の仕様を確認したが、「データは欠損する」という前提条件に真っ向から立ち向かう開発者たちの執念ともいえる仕様を見た。普段私たちが使っている携帯電話だったりインターネットだったりもこのような技術と仕様の上に成り立っている。たまにはTCPから降りてきて、よりハードなしかしチャレンジングな領域に思いを馳せてみてください。

## 執念の77bit

普段私たちがインターネット上でやりとりするデータは数キロバイトから数ギガバイトまで様々。現在のPCやルーター、スイッチングハブなどはそのくらいのデータ難なく処理するしなによりWiFiやLANケーブル、光回線ケーブルなどで結ばれた途切れることの無い線によって成り立っている。

これは携帯電話のネットワークも同じ。4G,5G通信は言ってみればたくさんの無線の交信を並列して中継基地をたくさん作って自分にとって近い距離の基地局と大容量のデータを素早くやり取りし、基地局から先は強靭な有線インターネットの世界で処理をしている。

ところが、もし山梨に居ながらにして東京の人とか北海道や九州沖縄の人、あるいは中国やアメリカ、地球の裏側と「直接」通信をするとしたら？ケーブルを使うと何万トンにもなるだろうし長さも計り知れない。だから電波を使う。しかし電波は「減衰」や「妨害」が存在する。

長い距離をかけて届く電波は色々な要因で「減衰」して信号が弱くなる。電波を出している人や設備がたくさんあると強い電波に「妨害」されてかき消されてしまう。そんな状況でも通信をしたい、その思いから開発された通信プロトコルがFT8。実際に通信可能なデータはたった77bit。UTF-8だと9文字に満たないこのデータを使って、自由テキストなら最大13文字、定型文ならコールサイン2つ＋位置情報＋αのやり取りができる。その方法はなんだろうか。

## 無線通信に最適化した圧縮術

今まで意図的に話題を避けてきたけれどこの通信プロトコルには「アマチュア無線」という文脈がある。相手のコールサイン（識別子）、受信した信号強度、送信場所と言った定型文のやり取りをすれば良いため圧縮ができる。

* コールサイン : 標準的なものは最大6文字程度。命名規則がだいたい決まっていて約2億6,800万通りしかなく、2^28(28bit)にちょうど収まる。文字をそのままUTF-8で送る（6文字なら48bit）より節約できる。さらに長い特殊コールサインは58bitや12bitのハッシュで扱う
* 位置情報 : 「グリッドロケーター」と言う地球上の位置を四角いタイルで区切った位置区分方式を使う。アルファベット2文字＋数字2文字の4文字形式は180×180=32,400通りしかなく、2^15=32,768に収まるため15bit（信号レポートやRRR/RR73/73なども同じ枠で表現）

これらに加えてどの定型文なのかを表すタグなどを含めて例えば以下のような文章を送ることができる

`CQ JK1TUT PM95`

もしこの12文字をUTF-8で送っていたら96bitだが、前述の圧縮方式を使えば実質的な情報量はコールサイン28bit＋グリッド15bit＝43bit程度。実際にはメッセージ種別を示す3bitなどを加えて常に固定77bitの枠に収まり、まだ余裕がある

個人的感想
普段何気なくUTF-8エンコードされた文字列をjsonで構造化してやり取りしていると、この圧縮手法にちょっと感動をする

## ここが本題：データは必ず欠ける、それでも直す ── LDPC

「電波」という物理現象を相手にする以上、データの欠落は避けて通れない。だから受信側に届くのは、綺麗に揃った0と1ではない。ノイズに埋もれた「たぶん1、でも自信度はこれくらい」という曖昧な値だ（軟判定 / soft decision）。FT8はこの曖昧さに **LDPC（低密度パリティ検査符号）** という誤り訂正で立ち向かう。今回いちばん感動したのがここ。データは失われる物という事実を受け入れた上で組まれたトレードオフに美しさがある。

### 送信側：厳密な数学で「保険」をかける

* 送信データ77bitに多項式 `0x6757` を当てはめて14bitのCRC（誤り検査符号）を計算。データ全体からチェックサムを求めるような物（CRCはチェックサムの一種で、単純な総和より誤り検出能力が高い）
* 77+14=91bitと、事前定義された生成行列G（83行×91列）の積を mod 2（XOR）で計算し、83bitのパリティ（誤り訂正符号）を得る
* データ77 + CRC14 + パリティ83 = 合計174bitを送る。これがLDPC (174, 91) 符号の1ワード

肝は、174bitの**正しい符号語は必ず「パリティ検査行列 H との積が0（mod 2）」になる**という厳密な代数的制約を満たすこと。送信側は数学的に隙のない「保険」をかけてから電波に乗せる。

### 受信側：厳密な制約を、確率で解く

ところが受信側に届くのは曖昧な174bit。そのまま H と掛けても、欠損のせいで0にならない（＝どこかが矛盾している）。ここで効くのが、**H がスパース（疎）＝ほとんど0で、たまに1**という性質。

* 各ビットは少数の検査式にしか関与せず、各検査式も少数のビットしか見ない
* だから「検査が0にならない」矛盾が起きても、原因のビットを局所的に絞り込める

この絞り込みを **確率伝播法（Belief Propagation）** で解く。「ビット」と「検査式」が二部グラフ上で、「君はたぶん1だと思う」「いや、私の式が成り立つには0のはずだ」と確からしさのメッセージを交換し合い、全体の矛盾が最小になる解へ少しずつ歩み寄っていく。多くの信号はこれを数回まわすだけで復号できる。弱すぎて収束しないときは、より重い OSD（順序統計復号）にフォールバックする。

ここが面白い。**仕組みは厳密な線形代数なのに、解く過程は「みんなで確からしさを持ち寄って一番もっともらしい答えに歩み寄る」という確率論的な交渉**になっている。数学で受け止めて、確率で押し返す。

### 最後の番人：CRC

復元した77bitから再びCRCを計算し、受信したCRCと突合する。一致すれば「確かに正しく直せた」と確信して画面に表示、一致しなければ捨てる。確率で殴って、最後は厳密な検査で答え合わせをする二段構え。

> おまけ：強い信号を復号できたら、その波形を再合成して受信音から「引き算」する。すると裏に隠れていた弱い信号が顔を出し、2回目・3回目のパスで拾える（多パス復号）。同じ周波数に重なった2〜3局を引き剥がして読むこともある。


## 15秒に詰め込まれた絶対に通信をしようという意思

FT8はGMTの毎分0秒～15秒、15秒～30秒、30秒～45秒、45秒～60秒の15秒サイクルで送信受信を切り替えなければならない。実際の送信は1シンボル0.16秒×79シンボル＝約12.6秒で、残りの約2.4秒が時刻同期やデコードのマージンになる。だから全員が正確な時計（PCのNTP同期）を前提にしている。

1回送ったデータが相手側で受信、または復元できなかったとしても15秒後にリトライできるという意味。1度駄目でも2度、3度と繰り返すことで確率論的な復元アプローチの成功率を上げようと言う作戦。

また、すでに交信中の相手がいる場合は相手のコールサインや次に送られてくるメッセージタイプを受信側で推論できる（a priori情報）。これがあると、デコーダーは未知の77bitを総当たりする代わりに残り15bit程度を決めるだけで済むため、探索すべきビットが約80%減る。

## 会話の文脈を機械が持つ ── ステートマシン

なぜ「次に来るメッセージ」が予測できるのか。FT8の交信は決まった型で進むからだ。`CQ → 応答 → 信号レポート → レポート受領 → ラジャー → 73(さよなら)` という流れを、WSJT-Xは6状態のステートマシン（Calling / Replying / Report / Roger Report / Rogers / Signoff）として管理している（仕様書にもUMLの状態遷移図で載っている）。

状態が分かれば次に来るメッセージの型が絞れる。さっきの a priori 情報の正体はこれだ。**「会話の流れ」という人間には当たり前の文脈を、機械が状態として保持しておくことで、微弱信号の復元を助けている。** 15秒という短いサイクルでは人間がボタンを押す暇もないので、この自動応答（Auto Seq）が事実上必須になる。

ちなみに設計者は「完全ロボット運用」を嫌っていて、WSJT-Xは交信の開始だけは必ず人間にやらせる仕様になっている（途中の応答は自動化するが、起点は人間）。

## まとめと今後

Webアプリとかクラウドインフラとかを触っていると気にも留めない物理的な意味でのデータ通信の仕組み。しかも綺麗に整頓されたケーブルでは無くてノイズや自然環境の影響を受ける微弱電波の世界でどうにかして通信をしてやろうという執念にも近い物を感じた。

今回いちばん伝えたかったのは、「データは必ず欠ける」という前提への向き合い方が一つじゃない、ということ。**厳密な数学（LDPC）を確率（Belief Propagation）で解き、1回の確率的な勝負を15秒ごとの繰り返しで取り返し、会話の文脈をステートマシンで持って探索空間そのものを削る。** レイヤーは違うのに、全部が「微弱電波でどうにか通信する」という一点に向けた最適化になっている。この多層的なトレードオフの効かせ方に、私は感動した。

今回説明したのはFT8という仕様におけるデータ変換の部分のみ。実際には電波に乗せる変調、電波からデータを取り出す復調と言うプロセスもあるがその話はまた別で。

ちなみにFT8の開発者ジョゼフ・テイラー氏（K1JT）は、教え子のラッセル・ハルス氏とともに連星パルサー（PSR B1913+16）の発見で1993年のノーベル物理学賞を受賞している。受賞理由は「新しいタイプのパルサーの発見と、それが重力研究に開いた新たな可能性」。連星をなす2つの中性子星が発する微弱なパルスの到達時刻を精密に解析したところ、公転周期がわずかずつ縮んでいた。これが一般相対性理論の予言する重力波放出（によるエネルギー損失）とぴたり一致し、重力波の存在を**間接的に裏付ける**初の証拠となった（直接検出は2015年のLIGO）。

そして、今日この発表の山場に据えたLDPCのような誤り訂正符号は、いまやSSD（NANDフラッシュ）の記録、WiFi、5Gといった身近な通信・記録の世界でも当たり前のように使われている。微弱電波からどうにかデータを拾うための執念が、めぐりめぐって我々のインフラを支えている。
